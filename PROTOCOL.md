# TP-Link Archer panel protocol (4G/5G SIM series, "GDPR encrypt")

Reconstructed by reverse engineering (static analysis of `js/tpEncrypt.js`,
`js/gdprProxy.js`, `js/encrypt.js`, `js/lib.js`, `js/oid_str.js` from the
WebUI, plus capture/verification of real traffic generated by the browser)
against an **Archer NX200** (5G AX1800), firmware `1.2.0 3.0.0 v60e0.0
Build 250725 Rel.73467n`. The crypto/session scheme is shared across
several Archer routers with this WebUI ("GDPR encrypt"); the names of the
application OIDs (SMS, LTE, etc.) are specific to the LTE/5G module and
need to be re-verified on other models.

## 1. Overview

All authenticated operations (reading/writing any data: SMS list, sending
an SMS, network status, etc.) go through a **single endpoint**:

```
POST /cgi_gdpr?9
Content-Type: text/plain

sign=<RSA signature, hex>\r\n
data=<AES-128-CBC-encrypted payload, base64>\r\n
```

The response body is just the base64 string of the AES-encrypted payload
(no `sign=`/`data=` wrapping in the response). The plaintext payload, both
in the request and in the response, is a compact JSON object (no extra
whitespace, as produced by `JSON.stringify`) shaped like:

```json
{"data": {"...": "..."}, "operation": "so|go|gl|cgi", "oid": "OID_NAME"}
```

- `operation`: `"go"` = get (read), `"so"` = set (write/set a parameter),
  `"gl"` = get list (read a list of items), `"cgi"` = invoke a special
  endpoint for `oid` (used only by login).
- `oid`: symbolic name of the data object (e.g.
  `DEV2_LTE_SMS_RECVMSGENTRY`), or the path `/cgi/login` for login.
- `data`: the call's parameters. Almost always includes `"stack"` and
  `"pstack"`, two strings like `"0,0,0,0,0,0"` that index the object
  instance in the router's internal data model (see §5).

There is **no "read-only, unauthenticated" endpoint** besides
`/cgi/getGDPRParm` (RSA bootstrap) and `/cgi/getBusy` (status of "is
someone logged in?"): everything else requires the full handshake
described below.

## 2. Login handshake

### 2.1 RSA bootstrap — `POST /cgi/getGDPRParm` (unauthenticated)

Request: `POST` with empty body. Response: "eval-able" JavaScript text
(not JSON), e.g.:

```js
var adminSetting=0;
var userSetting=1;
var logoUrl="";
var ee="010001";
var nn="D9FEB17A22CF0C147D4A1939A7A108B71A0F9E25AC9062084C2FD2A19FC11A875969B9D1124A943BD72B9CB351D3197245995CE4555B0481C55F4DBAECBCF271";
var seq="1049343027";
$.ret=0;
```

- `nn`/`ee`: RSA public modulus and exponent, **512-bit** (128 hex
  characters), exponent typically `010001` (65537).
- `seq`: an integer used as the base of the anti-replay counter. **Stays
  fixed for the entire session**: it must not be re-requested for calls
  after login (the original client only re-reads it because it reloads
  the whole page after login, not because a new value is needed).

### 2.2 Encrypting the login payload

1. Generate an AES-128 key and IV, **any 16 ASCII bytes** each (the
   original client uses digits from `timestamp + random`, but any 16-byte
   string works: the key is exchanged encrypted via RSA anyway and used
   only for this session).
2. `hash = MD5(username + password)`, lowercase hex. `username` **defaults
   to `"user"`**, not `"admin"`: on the Archer NX200 (and on models with
   `INCLUDE_USER_RESTRICTION=1` and no username field in the login GUI)
   the account matching the panel password is the "user" one
   (`adminType="user"` on the page), not "admin" — verified:
   `MD5("user"+password)` matches exactly the hash used by the real
   client.
3. Plaintext payload:
   ```json
   {"data": {"UserName": "<base64(username)>", "Passwd": "<base64(password)>",
             "Action": "1", "stack": "0,0,0,0,0,0", "pstack": "0,0,0,0,0,0"},
    "operation": "cgi", "oid": "/cgi/login"}
   ```
4. `cipher_b64 = AES-128-CBC-PKCS7(payload_json, key, iv)`, then base64.
5. Signature: the string to sign is
   `"key=<key>&iv=<iv>&h=<hash>&s=<seq + character length of cipher_b64>"`.
   **Note**: `s` is not simply `seq`, but `seq + len(cipher_b64)`, and this
   calculation is repeated for every call (see §3); `seq` itself, however,
   never changes within the session.
6. `sign = RSA_raw_no_padding(string_to_sign, nn, ee)` (see §4).
7. HTTP body: `"sign=" + sign + "\r\ndata=" + cipher_b64 + "\r\n"`, sent as
   `POST /cgi_gdpr?9` with `Content-Type: text/plain`.

### 2.3 Login response

- **HTTP 200**, header `Set-Cookie: JSESSIONID=<30 hex chars>; Path=/;
  HttpOnly` (see §6.1).
- Body: base64 AES that decrypts (with the same key/iv chosen in step 1)
  to `"$.ret=0;"`, sometimes followed by a NUL padding byte (`\x00`) — it
  must be discarded, it's not part of the message. `$.ret=0` means
  success; other codes mean wrong credentials or other problems (not
  mapped in detail: treat any value other than 0 as failure).

From this point on, **key/iv/hash/seq stay fixed for the whole session**:
subsequent calls don't retransmit them (except `seq`, indirectly, in the
`s` computation).

## 3. Post-login data calls

Same transport scheme (`POST /cgi_gdpr?9`, body `sign=...&data=...`), but:

- **Payload**: `{"data": {...}, "operation": "so"|"go"|"gl", "oid": "..."}`
  (no more `UserName`/`Passwd`/`Action`).
- **Signature**: the string to sign is just `"h=<hash>&s=<seq+len(cipher_b64)>"`
  — **without** `key=`/`iv=` (the server already remembers them from the
  session). Verified byte-for-byte: for a real input, the RSA signature
  computed with this scheme matches exactly the one produced by the JS
  client.
- The response decrypts to "real" JSON (spaced, not compact):
  `{"data": {...}, "operation": "...", "oid": "...", "success": true|false[,
  "errorcode": N]}`.

### 3.1 Required headers on data calls (the trickiest part)

Besides the signed body, **two elements not documented in the static JS
sources** are required, or the router responds `406 Not Acceptable` to any
`so`/`go`/`gl` call (login alone works even without them):

1. **`JSESSIONID` cookie** received at login (§2.3). It's marked
   `HttpOnly`: **invisible to `document.cookie` on the browser side**
   (which is why an analysis that only inspects `document.cookie` wrongly
   concludes that the panel "doesn't use cookies"). It must be read from
   the raw HTTP headers of the login response and sent back in
   `Cookie: JSESSIONID=...` on every subsequent request.
2. **`TokenID` header**, a second session token (30 hex characters, same
   format as JSESSIONID but a different, independent value) that the
   router **embeds server-side in the home page's HTML**, in a tag like:
   ```html
   <script type="text/javascript">var token="63d8d4da2e53f658fbd9a0f76aaf7e";</script>
   ```
   This script is generated **only if the request to `GET /` carries a
   valid `JSESSIONID` cookie** (with an anonymous session it doesn't
   appear at all) — which is why it's never found by searching for
   "tokenid" in the static `.js` files: it's never assigned there, it's
   injected by the server into the HTML per session. So the flow is:
   log in → **do a `GET /` with the session cookie** → extract `token`
   with a regex like `var\s+token\s*=\s*"([0-9a-fA-F]+)"` → use it as the
   `TokenID: <token>` header on all subsequent calls.

   Verified experimentally (from the context of the authenticated page,
   not by deduction): with the correct `TokenID` header the call returns
   `200`; with `TokenID: 0` (or missing, or a randomly generated but
   internally consistent value) it **always** returns `406`, regardless of
   signature/oid/data.

Without either of these two, the observed behavior is **inconsistent**:
depending on the case, the router responds with a clean `406`, or closes
the connection mid-way (`Empty reply from server` / `Connection reset`) —
behavior typical of an embedded backend bug when it receives
"structurally valid but unauthorized" requests, not a clean application
error. Don't rely on the error code to figure out what's missing: if a
post-login call always fails regardless of oid/data/signature, the number
one suspect is a missing or expired cookie or token.

## 4. "Raw" RSA signature without padding

The client (the `jsbn` library bundled in `js/encrypt.js`) uses 512-bit
RSA **without PKCS#1 padding**:

1. The message to sign is taken as UTF-8 bytes.
2. It's split into **64-byte** blocks (512 bits / 8: the modulus size).
   For the signatures used here (a few dozen characters for data calls,
   ~90 for login) it's almost always **1 block** (data) or **2 blocks**
   (login, because of the `key=...&iv=...` prefix).
3. Each block is padded with **zero bytes on the right** up to 64 bytes
   (not cryptographic padding — literal zeros).
4. The padded block is interpreted as an **unsigned big-endian integer**
   (`m`).
5. `c = m^e mod n`.
6. `c` is printed in hex and **left-zero-padded to 128 characters** (64
   bytes) per block.
7. The blocks (if more than one) are concatenated in order.

In Python: `pow(int.from_bytes(padded_chunk, "big"), e, n)`, formatted as
`"%0128x"`. In Java: `new BigInteger(1, chunk).modPow(e, n)` (the sign
flag `1` = positive magnitude, equivalent to Python's unsigned
`int.from_bytes` — **do not** use the single-argument `BigInteger(byte[])`
constructor, which treats the first bit as a two's-complement sign).

The router **does not require any PKCS#1 padding** on the receiving end:
it uses exactly this same scheme server-side to decrypt the signature.

## 5. AES-128-CBC and the "stack" data model

- AES-128-CBC, PKCS7 padding (in Java: `"AES/CBC/PKCS5Padding"`, which for
  AES is the same algorithm). Key and IV are the 16 ASCII bytes chosen at
  login, used **directly** as key material (no KDF).
- The router's data model is the classic CWMP/TR-069 one: objects are
  "instances" indexed by a 6-component comma-separated `"stack"`
  (`"a,b,c,d,e,f"`), all `0` by default. **Many LTE objects require
  `stack: "1,0,0,0,0,0"`** (instance 1) and **not** `"0,0,0,0,0,0"`: using
  the wrong stack almost always produces `{"success": false, "errorcode":
  9003}` (instance not found), not a transport error. The observed SMS
  objects instead use `"0,0,0,0,0,0"` for the main object (`RECVMSGBOX`,
  `SENDNEWMSG`) but still `"0,0,0,0,0,0"` for the entries getlist
  (`RECVMSGENTRY`) — there's no single rule: **it must be checked per
  OID** by observing real traffic.
- "Set then get" pattern: for many paginated/parameterized reads (e.g. the
  SMS inbox) the client first does a `"so"` to set a parameter (e.g.
  `PageNumber`) on the object, then a `"go"`/`"gl"` to read its result —
  these are two separate calls, not one.

## 6. Session and limitations

### 6.1 No real "per-request" access control

Apart from cookie+token (checked only to accept/reject a single request),
the router **does not implement a per-client session** in the strict
sense: it allows **only one active administrative session at a time**
("Only one device can log in at a time" in the GUI). A new login
**automatically takes the place** of the previous one — via script, with
no confirmation required (the "do you want to force-logout the other
device?" dialog is pure client-side GUI sugar: the login HTTP request is
identical whether the user clicks "confirm" or nobody else is logged in).
Practical consequence: if you run a script and then log in from the GUI
(or vice versa), the previous session is replaced and you may have to
confirm the GUI-side popup by hand.

No explicit logout endpoint was found (it doesn't appear in the static
`.js` files: the "Logout" button's handler is part of content loaded/
decrypted dynamically after login, not inspected). In practice it's not
needed: the next session takes the active slot's place anyway.

**Confirmed practical note**: keeping the router's GUI open in a browser
(even just on the login page, being authenticated is not required) while
an automated client (a script or a NiFi processor) attempts to log in can
cause intermittent failures — including `406` on unauthenticated
endpoints like `/cgi/getGDPRParm` — because the automated client ends up
competing for the session slot with the browser page's background
polling. Closing the browser tab fixes the problem. If you run an
automated client on a tight loop/schedule (e.g. a NiFi processor with too
short a scheduling interval or "Concurrent Tasks" > 1), the same kind of
conflict can also occur between consecutive runs of the client itself: the
router's embedded webserver handles too-close/parallel login requests
poorly.

### 6.2 Embedded webserver bug on connection reuse

The router's webserver **does not correctly handle HTTP keep-alive** when
the request body contains literal CRLF sequences (as in the
`"sign=...\r\ndata=...\r\n"` format used here): reusing the same TCP
connection for two consecutive requests to `/cgi_gdpr` often produces a
`406` or an abrupt connection close, **even with an otherwise correct
payload**. A new TCP/TLS connection must be opened for every request (see
implementations: `requests.Session()` per call in Python, an `HttpClient`
per call in Java).

### 6.3 TLS certificate

The panel exposes HTTPS with a **self-signed certificate with no
subject/SAN at all** (`subject: [NONE]`, issuer CN like `TP-LINK SOHO
Router CA`). Any client must disable both trust-chain verification and
hostname verification (disabling trust errors alone is not enough:
hostname verification must be disabled too, or the TLS handshake still
fails on a name mismatch).

## 7. Verified OIDs

All confirmed against real traffic (decrypted with the observed session
key) or against direct router responses using the same scheme.

| OID | operation | stack | Notes |
|---|---|---|---|
| `/cgi/login` | `cgi` | `0,0,0,0,0,0` | Login only (§2). |
| `DEV2_LTE_SMS_RECVMSGBOX` | `so` then `go` | `0,0,0,0,0,0` | `so`: sets `PageNumber`. `go`: returns `totalNumber`, `unreadNumber`, `pageNumber`, `amountPerPage`. |
| `DEV2_LTE_SMS_RECVMSGENTRY` | `gl` | `0,0,0,0,0,0` | Returns an array of `{index, from, content, receivedTime, unread, stack}`: the SMS on the current page. |
| `DEV2_LTE_SMS_UNREADMSGBOX` / `_UNREADMSGENTRY` | as above | `0,0,0,0,0,0` | Unread only (used by the dashboard widget). |
| `DEV2_LTE_SMS_SENDNEWMSG` | `so` then `go` | `0,0,0,0,0,0` | `so`: `{index:"1", to, textContent}` → `{"success":true,"errorcode":0}`. `go` (polling): `{index, to, textContent, sendTime, sendResult, stack}`; `sendResult`: `"3"` = sending in progress, `"1"` = sent successfully (other values not mapped = likely error). |
| `DEV2_CELL_INTF_USIM` | `go` | **`1,0,0,0,0,0`** | `{status, IMSI, ICCID, MSISDN, PINCheck, PIN}`. |
| `DEV2_LTE_NET_STATUS` | `go` | **`1,0,0,0,0,0`** | `{sigLevel, connStat, roamStat, regStat, netType, srvStat, smsUnreadCount, ...}`. |
| `DEV2_LTE_LINK_CFG` | `go` | **`1,0,0,0,0,0`** | Data connection: `ipv4/ipv6`, `dns1v4/dns2v4`, `gatewayV4/V6`, `connectedBand`/`availableBand`, `roamingStatus`, `smsScAddress` (SMS center), `signalStrength`. |
| `DEV2_XTP_LTE_INTF_CFG` | `go` | **`1,0,0,0,0,0`** | Data counters: `totalStatistics` and `dailyFlow` (**bytes**, not GB — divide by 1024³ for the GB shown in the GUI), `rxFlow`/`txFlow`, `enableDataLimit`/`dataLimit`/`limitType`/`limitation`/`warningPercent` (data warning threshold, if configured). |
| `DEV2_XTP_LTE` | `go` | `0,0,0,0,0,0` | Modem module info: manufacturer, serial number, LTE module firmware version. |
| `DEV2_LTE_ISP_PROF` | `gl` | `0,0,0,0,0,0` | List of preconfigured APN profiles per carrier (not the active profile). |
| `DEV2_LTE_BANDINFO` | `go` | `0,0,0,0,0,0` | Active radio band/channel (values observed as "0" at idle). |

OIDs **attempted and resulting in an error** (`errorcode 9003`, "instance
not found") with `stack:"0,0,0,0,0,0"` — almost certainly requiring a
different, not-yet-determined stack, not unusable in absolute terms:
`DEV2_LTE_SERVING_CELL_INFO`, `DEV2_LTE_PROF_STAT`, `DEV2_LTE_PROFILE`,
`DEV2_LTE_ISP_PROF` (with `go` instead of `gl`).

**Warning**: calling an oid/operation that's invalid for the router does
not always produce a clean application-level error — in some observed
cases it caused an abrupt connection close (likely a crash of the backend
CGI process handling that specific request, not just a protocol-level
rejection). Every new OID should therefore be validated carefully, ideally
by first observing the real traffic generated by the GUI for that feature
instead of blind attempts.

## 8. What has NOT been determined

- The exact endpoint/format of **explicit logout** (§6.1) — not needed in
  practice, but not mapped.
- The correct `stack` for `DEV2_LTE_SERVING_CELL_INFO` (detailed
  serving-cell/band info: precise RSRP/RSRQ/SINR as shown in the GUI) and
  for the other OIDs listed as failing in §7.
- The full meaning of `DEV2_LTE_SMS_SENDNEWMSG`'s `sendResult` codes
  beyond `"3"` (in progress) and `"1"` (observed success).
- Whether/how a SIM `PIN` is handled by `DEV2_CELL_INTF_USIM` (the field
  exists, `PINCheck` was `"Off"` on the test device — not tested with an
  active PIN).
